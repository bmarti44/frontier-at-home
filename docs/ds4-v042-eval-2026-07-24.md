## SUPERSEDED by triage below: "drift" is a one-time lazy-init pool

Per-request attribution (scripts/dev/regression-suite.py ds4-mem-init, plus
/tmp/mem-triage runs) reframed the earlier conclusion: MemAvailable drops
~11.8-11.9 GiB on the FIRST generation only (measured at both ctx 65536 and
ctx 32768 — context-independent), then stays flat within measurement noise
across identical requests (drift over 5 further requests: -0.67 to +0.8 G),
plus ~0.6 GiB per retained warm bank for a 19K conversation. Nothing
releases at idle (5 min observed); everything returns at exit. The engine's
own comment names the contents: tmp pools, capture graphs, logits staging —
sized lazily at first use. The earlier "12 GiB per gauntlet round" reading
conflated this one-time cost + per-unique-prompt warm banks with ongoing
drift. Sizing rule for this host: weights (~81) + init (~12) + watchdog
floor (12) ≈ 105 GiB -> viable boot-clean, too tight with desktop apps.
Mitigation path: fire one warmup generation at startup so the memory gate
and watchdog baseline see steady state; cap the warm tier (bank count is
already bounded by DS4_BATCH_FIT_HEADROOM_MB); ask upstream for eager,
logged init-pool allocation.

## Historical (first reading, superseded): drift is NOT bank-count driven; spec needs banks

At `DS4_BATCH_FIT_HEADROOM_MB=22528` (max_seq 2), two full gauntlet rounds
still sank free 19.8 -> 7.6 -> 7.1 GiB — ~12 GiB of runtime growth
independent of bank count (warm tier / VMM slab / staging growth; no RAM
budget knob found for it; `DS4_KVSTORE_DEFAULT_MB` budgets the DISK tier
only). Memory fully recovers on process exit (114 GiB), so it is held, not
leaked — but the watchdog reads live MemAvailable, so it gates production
regardless. Side effect at max_seq 2: speculation disengaged (uniform
~20.5/17.0 plain-tier decode; JSON fell from 44 to 20.5), so starving banks
costs the headline decode wins. Upstream's own churn test reports 1.0 GiB
drift over an hour — our 18-request/12 GiB observation suggests a
host-or-workload-specific interaction worth reporting upstream with these
numbers. Next probes: DS4_CONT_WARM_GATE semantics, boot-clean host run,
upstream issue.

## The one open blocker: memory floor

Default bank sizing took free memory to **4.8 GiB** after the gauntlet — far
under the 12 GiB watchdog line. `DS4_BATCH_FIT_HEADROOM_MB=16384` reduced
banks (max_seq 21 -> 7) and the same suite bottomed at **10.8 GiB** — closer
but still under the line. Bank count is controllable; residual runtime
growth (VMM slabs, warm banks) needs either a larger headroom setting
(fewer banks; we need only 2-4 for the agent + utility pattern), a
boot-clean host measurement, or an upstream RAM budget for the warm tier.
Production integration is gated on demonstrating sustained free >= 12 GiB
under the burst suite.

## Verdict and what "implemented" requires

PROVES OUT on performance: ~1.6x prefill, sub-second warm agent turns that
survive restarts, +35-60% conversation-depth decode, spec bursts stable,
old context envelope obsolete. Remaining before production swap (protocol):
1. Memory bounding demonstrated (above).
2. Full qualification battery on the v0.4.2 binary: golden, parity,
   GSM8K/MMLU-Pro dev + holdout, HumanEval, 30-min soak (upstream's own
   battery reports HumanEval 149/164 and needles 70/70 on this quant —
   encouraging, not a substitute).
3. Vendor drop + build/weights manifests + security-review delta
   (docs/ds4-security-review.md refresh; new surface: disk-KV tier,
   ds4_kvstore/rax), launcher (20_serve_ds4.sh) update for v0.4.2 flags,
   DECISION addendum superseding the ≤28K envelope exception, serving-swap
   plan with llamacpp as documented fallback.
