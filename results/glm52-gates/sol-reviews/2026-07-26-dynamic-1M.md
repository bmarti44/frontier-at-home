Blunt answer: dynamic 1M is not interactive on this box for either GLM-5.2 or DSV4.

- GLM cannot allocate 1M with today’s F32 cache and would need at least roughly 10.5 hours even if memory were fixed.
- DSV4 can probably construct 1M dynamically in an experimental configuration, but not within 30 minutes: the optimistic, memory-unsafe configuration projects to 1.5–3 hours; the smaller ubatch configuration with a chance of fitting projects to 3–5 hours. No local 1M run verifies either range.
- Thus “1M context” means supported position/cache architecture and demonstrated long-context quality—not an interactive TTFT claim. The official config sets `max_position_embeddings=1048576`; it does not specify ingestion latency. [DeepSeek config](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/config.json)

## 1. Actual dynamic-1M cost

First, one correction: your conclusion that selection is per token is right, but the 5.38 PB / 5.5-hour traffic number does not describe the active production path.

The scalar loop is disabled and the batch indexer is enabled in [ds4.c](/tmp/claude-1000/-home-bmarti44-spark-deepseek-v4-flash/3109d29d-cd62-4998-a2e1-bfb6e29288b5/scratchpad/engine-src/ds4.c:40843). The default non-quality CUDA kernel stages one 128-row K tile and reuses it across 16 query tokens in [ds4_cuda.cu](/tmp/claude-1000/-home-bmarti44-spark-deepseek-v4-flash/3109d29d-cd62-4998-a2e1-bfb6e29288b5/scratchpad/engine-src/ds4_cuda.cu:26289).

Therefore:

- 5.376 PB is the logical per-query K volume.
- The active kernel issues approximately 336 TB of K loads, not 5.376 PB.
- At 273 GB/s, that is 20.5 minutes of bandwidth-equivalent work.
- It also writes about 42 TB of scores: another 2.6 minutes.
- It performs approximately 86 PFLOP of indexer dot products.
- Exact top-k adds a very large, currently unmeasured cost.

The complexity is still quadratic and every token still gets its own selection. The 5.5-hour K-read number applies to the scalar/quality path, not today’s serving path.

| Model at 1M | Linear work | Long-context work | Memory | Honest result |
|---|---:|---:|---:|---|
| GLM-5.2 | 10.1 h | ≥23 min K loads/writes, plus 86 PFLOP and unmeasured top-k | 186.5 GiB context alone versus 119.7 GiB physical | Cannot run today; hypothetical optimistic time ≥10.5 h |
| DSV4, 1,000,000 | 35.7 min | Indexer 672 TB ≈41.0 min; HCA K+V ≈160 TB/9.8 min; other attention and score traffic ≈43.8 TB/2.7 min | Possible only narrowly with a one-slot, small-ubatch setup | Idealized additive model ≈89 min before top-k and inefficiency |
| DSV4, 1,048,576 | 37.4 min | Corresponding traffic model ≈58.7 min | ub2048 leaves only 1–4 GiB; ub512 leaves 10.5–12 GiB, both below the production floor | ≈96 min optimistic floor; practical planning 1.5–5 h |

The DSV4 indexer kernel assigns a CUDA block to one query token, so unlike GLM’s kernel, it does not explicitly reuse K across query tokens; see [lightning-indexer.cu](/home/bmarti44/spark-deepseek-v4-flash/vendor/llama.cpp/ggml/src/ggml-cuda/lightning-indexer.cu:18). Cache may reduce some physical DRAM traffic, so the 41–45 minutes is a current-kernel traffic model rather than a measured theorem.

Independent evidence supports the nonlinear estimate: upstream measured 524K dynamic prefill in 1,860.6 seconds on an RTX Pro 6000 Max-Q system whose short-context rate was substantially faster than this Spark. A fitted `aN+bN²` curve gives approximately 94 minutes at 1M and 102 minutes at 1,048,576 on that faster system. [Upstream llama.cpp measurements](https://github.com/ggml-org/llama.cpp/pull/24162)

Locally, the documented capacity forecast is:

- ub2048: 1.5–3 hours, but memory-unsafe.
- ub512: 3–5 hours, with marginal memory headroom.

Those are explicitly forecasts, not acceptance measurements. See [big-context plan](/home/bmarti44/spark-deepseek-v4-flash/docs/bigctx-plan-sol-2026-07-16.md:90).

So the precise verdict is:

- DSV4 dynamic 1M: probably technically constructible over hours, after reconfiguration; not locally verified and not production-safe.
- GLM dynamic 1M: impossible in the current representation; even after a memory redesign, not interactive.
- Dynamic 1M within 30 minutes: nothing among these two models reaches it on this box.

## 2. Can exactness break the quadratic?

| Candidate | Exact? | Verdict |
|---|---|---|
| Shared selection for B tokens | No | Approximately B-fold indexer/top-k reduction. B=1 is the only output-safe value established. The NLL-safe value of B>1 is unverifiable without experiments. |
| Hierarchical centroids | Normally no | Approximate ANN unless every rejected cluster has a proved upper bound. Exact fallback has worst-case full scanning. |
| Previous top-k ∪ recent ∪ sample | No | Adjacent-query selection overlap has not been measured. Query similarity alone cannot prove top-k identity. |
| FP8/FP4 index cache | No | GLM K traffic falls 4×/8× from F32, but rank-2048/2049 flips remain possible. DSV4 starts at F16, so its reduction is only 2×/4×. |
| Exact bound pruning | Data-dependent exact, not guaranteed sublinear | Can return identical top-k, but no evidence it will prune enough in this 128-dimensional index. |

An exact block bound is possible. For cluster center \(c\), radius \(r\), and score

\[
f(k)=\sum_h w_h\operatorname{ReLU}(q_h\cdot k),
\]

a safe bound is:

\[
UB =
\sum_{w_h\ge0} w_h\max(0,q_h\cdot c+\lVert q_h\rVert r)
+
\sum_{w_h<0} w_h\max(0,q_h\cdot c-\lVert q_h\rVert r).
\]

A block may be skipped when this is below the current kth score. That is exact because ambiguous blocks fall back to full scoring.

The problem is effectiveness:

- Simple max-norm bounds will probably prune almost nothing because the keys pass through normalization and block maximum norms will be similar.
- Ball bounds become loose in 128 dimensions.
- Top-2048 is much harder to prune than top-1: at 1M it is the top 0.205%, so the threshold is not an extreme maximum.
- There is no worst-case exact sublinear algorithm here: an uninspected row may always be the missing winner. Trees and bounds only improve favorable datasets.

Therefore exact pruning gain is currently unverifiable. It should receive zero capacity credit until a replay benchmark proves exact ID equality and measures pruning after bound overhead.

There are, however, exact constant-factor opportunities:

1. **Replace the current bitonic full-sort top-k.** At 1M rows, one query performs roughly 492 separate 4096-element sort networks, or about 78.6 million compare-exchanges per layer. Cumulatively across 1M queries and 21 layers, this is on the order of \(8\times10^{14}\) compare-exchanges. An exact radix/select/gather algorithm followed by ordering the final 2048 with the existing tie rule could reduce this drastically without changing selected IDs. It does not remove the quadratic score scan.

2. **Store GLM indexer K as FP16.** The fast kernel already converts every F32 cached K value to FP16 before WMMA. Storing that identical rounded FP16 value earlier should therefore preserve current fast-path results bitwise, provided the store uses the same rounding. This halves K traffic: 336→168 TB at 1M. It must be A/B-tested and does not apply to quality mode.

3. **Reuse one K tile across 32/64 queries.** The current reuse width is 16. Executing two or four unchanged 16×16 WMMA query tiles inside one block could cut K loads another 2–4× while retaining the same individual MMA operations. Again, this changes constants, not the exponent.

None of these turns GLM’s 10.1-hour linear component into an interactive prefill.

## 3. True GLM interactive ceiling

These are warm-service prompt-ingestion limits using the measured 23–32 tok/s. They exclude process/model startup. Because the indexer/top-k adds nonnegative work, the time-derived ranges are upper bounds.

| TTFT budget | Time-derived GLM ceiling | Current `-c 32768` profile | After decode-protected admission + cache-slot GEMV |
|---:|---:|---:|---:|
| 60 s | ≤1,380–1,920 tokens | 1.4–1.9K | No change |
| 5 min | ≤6,900–9,600 tokens | 6.9–9.6K projected | No change |
| 30 min | ≤41,400–57,600 tokens | **32,768 configured ceiling** | No change |

Verification status matters:

- 5,047 tokens: verified in 139–165 seconds.
- 11,648 tokens: verified in 346 seconds.
- Full 32,768-token cold construction: not measured. Linear projection is 17.1–23.7 minutes, so it should fit 30 minutes, but that is not an acceptance result.
- With the context cap raised, 41–58K is only the linear time bound. The actual ceiling is unverifiable until a long-context top-k profile is run.

The named fidelity-free levers do not move this table:

- Decode-protected admission protects active decode latency; it does not accelerate isolated prefill.
- GEMV from expert-cache slots is a decode path.
- No useful exact pruning rate has been demonstrated.
- Exact FP16 index-K storage would save only roughly 1–2 seconds around 50K; it does not move the ceiling materially.

The honest user-facing ceiling today is therefore **32K admitted context for a 30-minute budget, with only 11.6K dynamically verified**. For a five-minute product SLA, advertise approximately **5K verified**, not 9K.
