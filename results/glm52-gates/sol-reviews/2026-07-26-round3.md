### ITEM 1 — CORRECT-BUT-RISKY

The round-2 sequence is closed for the current `ds4.c` lifecycle. Every engine/error close with GPU state reaches `ds4_gpu_cleanup`; the only standalone support-model close occurs before GPU initialization. On reopen, both single- and multi-tier paths register the main map, forcing a generation bump. The surviving expert cache is then flushed before lookup; old prefetch slabs fail their generation check.

Remaining API-level failing sequence:

1. A is cached with tuple `(P, N, H, fd=5)`.
2. Without cleanup or `set_model_fd(-1)`, unmap/close A.
3. Open B; it reuses address `P`, size `N`, fd number `5`, and the same first 4 KiB, but has different expert data.
4. Call `ds4_gpu_set_model_fd(5)` and register `(P,N)`.
5. No field differs, so no bump: A’s cached slabs and private prefetch fd remain eligible.

Current `ds4.c` does not perform that sequence. If positive-fd hot replacement is within the setter’s contract, verdict becomes BROKEN.

Two lifecycle risks remain:

- The prefetch worker is never stopped/rebound. Legitimate reopen is safe, but disables prefetch permanently and leaks its threads/private fd.
- `g_support_host_base/size/bias` are not cleared. A later main mapping reusing the old support address can be wrongly offset in multi-tier lookup. Separate from generation safety, but real.

### ITEM 2 — SUBSTANTIALLY CORRECT

The arithmetic and thrashing inference are right for these large chunks. The recorded sweeps total 171.0 and 168.1 GiB across 75 layers, versus roughly 68 GB of cache: about 2.5×, not materially different from your 2.6× estimate. “Regardless of token count” is too broad; it holds here because both 2,048- and 2,999-token batches already saturate nearly all 256 experts.

The null is credible:

- `452 → 0` proves the fix arm was active.
- The escape hatch reproduces the observable old flush cadence; it omits a redundant double generation increment, but both increments previously preceded one cache observation.
- `9.3% → 12.6%` means only a small amount of I/O was actually avoided. Dense/indexer compute and nonexpert model loading can further bury that saving.

Caveats: these numbers are n=1 per arm, and cross-process page-cache state was not reset. Therefore claim “no measurable benefit observed on this fixture,” not universal “no performance benefit.”

KEEP is reasonable as a cache-invalidation/lifecycle fix. It is not an inference-correctness fix—the old behavior was output-safe but wasteful.

### ITEM 3 — MECHANICALLY FALSE; DO NOT RUN AS WRITTEN

`DS4_METAL_PREFILL_CHUNK` does not reach the GLM CUDA session path. GLM bypasses `ds4_prefill_cap_for_prompt()` and uses the indexed-prefill machinery:

- `full_kv_cache` is hardcoded false.
- `indexed_prefill_cap` is 4096.
- `glm_graph_limit_indexed_prefill_chunk()` forbids crossing the 2,048-row indexer top-k boundary.

Thus 5,047 tokens become exactly:

- 2,048 tokens → `slots=16384`
- 2,999 tokens → `slots=23992`

Setting the environment variable to 8192 changes none of that. Even enlarging the indexed cap alone would not remove the 2,048 bridge split.

At actual harness settings, 8192 changes no workspace, KV allocation, context limit, or numerics because it is a no-op. A real implementation would require resizing indexed workspaces/memory guards and redesigning the top-k bridge; combining batches could alter floating-point results and must be fidelity-gated.

Harness flaws:

- Layer-3 counting is valid only for this selected-expert path. Full-layer mapping or a fallback produces no such line. Count `DS4_GLM_SYNC_TRACE` branch/position/chunk records instead.
- `prefill_mib` is logical requested slab volume, not physical NVMe bytes or misses.
- Environment sanitization misses generation, token-prefill, and full-layer-prefill knobs.
- HTTP/output equality are reported but not enforced.
- OS page cache is retained across processes. ABBA balances linear drift, not first-run/nonlinear warming.
- n=2 is enough to detect a genuinely huge effect, not establish a null or modest effect.

Prediction: both arms execute two sweeps, report approximately the same ~339 GiB logical slab volume, and have identical output. Causal TTFT change: exactly 0%; observed difference should be noise, plausibly within ±3–5%.

### ITEM 4 — STILL UNSUPPORTED

- Keep-7/keep-6 gains are supported only as one-fixture observations. General decode gains, confidence intervals, and causality remain unsupported until the trajectory-controlled pass finishes.
- Warm TTFT 1.755 s is supported only for steady-state exact replay with disk-KV checkpointing—not ordinary same-process replay or multi-turn traffic.
- `unique=8/7/6` supports reduced logical loader slab bytes. It does not by itself prove proportional physical NVMe traffic or kernel-compute reduction.
- Gen3 remains statically reviewed but unbuilt/unrun; positive-fd replacement and support-global teardown remain uncovered.
