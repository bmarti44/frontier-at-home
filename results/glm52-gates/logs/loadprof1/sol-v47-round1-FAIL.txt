1. MEDIUM — Pin-registration failure is not fail-open. A failed cudaHostRegister leaves the host thread’s CUDA error state set; cudaGetErrorString does not clear it. A later kernel-side cudaGetLastError can therefore report the old registration failure and abort inference even though pageable fallback copies succeeded. This is realistic under pinned-memory exhaustion or platform limits. Clear the expected error with cudaGetLastError after logging, while ensuring a genuine prior asynchronous error is not swallowed. [CUDA error-state semantics](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html)

2. MEDIUM — Deferred fill failure can poison a supposedly valid cache entry. cuda_expert_cache_insert publishes the key before its three D2H operations complete. If a fill fails asynchronously, the final synchronization rejects the current load, but only g_stream_selected_cache is invalidated; the persistent slot remains mapped. A later request, if the CUDA context remains usable, can hit stale or partially filled bytes. A subsequent enqueue can also surface the preceding job’s error and demote the wrong slot. Publish slots only after successful synchronization, or flush/demote all pending fills whenever the synchronization fails.

3. MEDIUM — The registered arena has no unregister lifecycle. The same-layout model-generation flush itself is safe: it only clears metadata, and old/new DMA remains stream-ordered. However, ds4_gpu_cleanup or a reload to an incompatible slab layout leaves roughly 67 GiB registered indefinitely; persist_ok then remains false while the unusable arena stays pinned. Later model/KV allocation can fail or the process can be killed under memory pressure. Track registration state and call cudaHostUnregister after synchronization during actual cache/backend teardown; do not unregister merely for a same-layout generation flush. NVIDIA explicitly requires registered memory to be unregistered and warns that excessive pinning removes pageable capacity. [CUDA host-registration documentation](https://docs.nvidia.com/cuda/archive/12.6.2/cuda-runtime-api/group__CUDART__MEMORY.html)

4. LOW — RLIMIT_MEMLOCK is not a reliable safety boundary here. Your measured 67 GiB registration succeeding under a 15 GiB limit demonstrates that this driver path does not enforce that limit as expected. On another driver it may reject registration, triggering finding 1; on this driver it may lock the full arena and trigger finding 3. Treat available-memory headroom, not RLIMIT_MEMLOCK, as the operational guard.

5. LOW — LOADPROF fields are misleading outside the tested six-worker configuration. With fetch_threads below 2, misses never enter miss_jobs, so miss, fetch_ms, and fill_ms report zero despite synchronous fetches and fills. After v4.7, hit_ms and fill_ms measure cudaMemcpyAsync enqueue time, not DMA completion; completion time falls into total_ms at the later synchronous remap copy. Count misses independently and rename these fields enqueue_ms, or use CUDA events.

6. LOW — ec_prof_now_ms ignores clock_gettime failure and reads an uninitialized timespec, which is C++ undefined behavior. Normal Linux CLOCK_MONOTONIC calls should succeed, but the strict claim that profiling cannot affect outputs is not defensible under an injected or platform error. Zero-initialize the structure and disable profiling or return a sentinel on failure.

7. LOW — Stream safety depends on the current build mode. The reviewed nvcc invocation uses legacy-default-stream semantics, so the hit/fill ordering and the 7,398-versus-256 LRU argument hold, and synchronous worker copies protect bounce-buffer reuse. If a future build enables per-thread default streams, literal stream 0 in worker and main threads becomes different streams, allowing worker H2D transfers to race main-thread fills and kernels. Use cudaStreamLegacy explicitly or add a compile-time guard. [CUDA default-stream semantics](https://docs.nvidia.com/cuda/cuda-driver-api/stream-sync-behavior.html)

The profiling fprintf does not corrupt the HTTP protocol or stdout under the current server architecture: responses use sockets and the call targets stderr. It can still block inference if a pipe/journal stops draining, terminate on SIGPIPE if its pipe closes, or mix with stdout when an operator explicitly redirects 2>&1. That is an availability risk confined to the profiling gate.

The byte-identical fixtures validate the successful, same-model path; they do not exercise registration failure, deferred DMA failure, incompatible reload, or cleanup.
